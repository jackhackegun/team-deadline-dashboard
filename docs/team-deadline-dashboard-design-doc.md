# 팀 프로젝트 데드라인 대시보드 — 설계문서

## 1. 개요

### 1.1 프로젝트명
팀 프로젝트 데드라인 대시보드 (Team Deadline Dashboard)

### 1.2 배경 및 목적
학교 팀플/사이드 프로젝트에서는 각자 맡은 할 일과 마감일이 흩어져 있어, 누가 무엇을 아직 안 했는지 파악하기 어렵다. 본 서비스는 팀원별 할 일과 마감을 한 화면에 모아 진행률을 게이지(원형 %)로 시각화하고, 마감이 임박했는데 완료되지 않은 항목을 한눈에 강조해 보여준다.

### 1.3 핵심 가치
- 팀 전체 진행 상황을 별도 취합 없이 대시보드 하나로 확인
- "누가 안 했는지"를 멤버별 진행률·경고 배지로 즉시 파악
- 여러 팀 프로젝트를 동시에 진행하는 학생의 실제 상황 반영 (팀 전환 지원)

## 2. 요구사항 정의

### 2.1 기능 요구사항
| ID | 요구사항 |
|----|----------|
| F1 | 회원가입/로그인 (계정 기반) |
| F2 | 팀 생성 및 초대코드로 팀 합류 |
| F3 | 한 사용자가 여러 팀에 소속되어 전환 가능 |
| F4 | 팀원 누구나 할 일 생성 및 담당자 지정 가능 (권한 제한 없음, 역할만 구분) |
| F5 | 할 일 안에 로드맵(하위 체크리스트) 단계를 추가하고 완료 토글 가능. 단계가 없는 할 일은 자체적으로 완료 토글 |
| F6 | 팀 전체 진행률 게이지 표시 (완료된 로드맵 단계 수 ÷ 전체 단계 수 기준, 단계 없는 할 일은 그 자체를 1단위로 취급) |
| F7 | 멤버별 진행률 게이지 및 미완료 할 일 수 표시 |
| F8 | 마감 임박/초과 항목 시각적 경고 (색상 강조) |
| F9 | 마감 D-1 이메일 알림 |

### 2.2 비기능 요구사항
| ID | 요구사항 |
|----|----------|
| N1 | 소규모 팀(수 명~십수 명) 기준 성능이면 충분, 대규모 동시접속 고려 안 함 |
| N2 | 별도 실시간 인프라(WebSocket) 없이 폴링으로 갱신 |
| N3 | 배포 비용 최소화 (단일 백엔드 프로세스, 무료/저비용 호스팅 대상) |

## 3. 시스템 구성도

```
┌────────────────────┐        HTTPS / JSON         ┌─────────────────────────────┐
│   React (Vite) SPA │ ───────────────────────────▶│         FastAPI Server       │
│  - 로그인/팀목록    │◀─────────────────────────── │  - Auth (JWT)                │
│  - 대시보드 화면    │      60초 폴링 갱신          │  - REST API (teams/tasks)    │
└────────────────────┘                              │  - Dashboard 집계 로직        │
                                                     │  - APScheduler(일 1회 D-1체크)│
                                                     └───────────┬─────────────┬───┘
                                                                 │             │
                                                         SQLAlchemy        smtplib
                                                                 │             │
                                                        ┌────────▼───────┐  ┌──▼───┐
                                                        │  PostgreSQL DB │  │ SMTP │
                                                        └────────────────┘  └──────┘
```

- 단일 FastAPI 프로세스가 API 서빙과 알림 스케줄링을 함께 담당 (모놀리스 구조).
- 실시간 갱신 대신 프론트에서 주기적 폴링.

## 4. ERD

```
User ───┬───< TeamMember >───┬─── Team
        │  (role: leader     │
        │   /member)         │
        │                    │
        ├───< Task (assignee_id) >─── Team
        └───< Task (created_by) >
                   │
                   └───< RoadmapStep
```

| 엔티티 | 주요 속성 |
|--------|-----------|
| User | id(PK), email, password_hash, name |
| Team | id(PK), name, invite_code |
| TeamMember | user_id(FK), team_id(FK), role |
| Task | id(PK), team_id(FK), title, assignee_id(FK→User), deadline, done(bool), created_by(FK→User), created_at, notified_at |
| RoadmapStep | id(PK), task_id(FK→Task), title, done(bool) |

- User ↔ Team은 TeamMember를 통한 다대다 관계 (한 사용자가 여러 팀 소속 가능).
- Task는 Team에 속하며, 담당자(assignee)와 생성자(created_by) 모두 User를 참조.
- RoadmapStep은 Task에 속하는 선택적 하위 체크리스트(0개 이상). 단계가 있으면 진행률은 단계 완료 비율로 계산되고, Task의 `done`은 모든 단계가 완료됐을 때 자동으로 true가 되어 직접 토글할 수 없다. 단계가 없으면 Task의 `done`을 직접 토글하며 그 자체가 1단위로 집계된다.
- 진행률/마감 임박 여부는 별도 저장 컬럼 없이 Task+RoadmapStep 집계로 조회 시점에 계산.

## 5. 화면 설계

### 5.1 화면 목록
| 화면 | 경로 | 설명 |
|------|------|------|
| 로그인/회원가입 | `/login`, `/signup` | 계정 인증 |
| 팀 목록 | `/teams` | 소속 팀 목록, 팀 전환, 팀 생성/합류 |
| 대시보드 | `/teams/:id` | 메인 화면 |

### 5.2 대시보드 레이아웃
```
┌───────────────────────────────────────────────┐
│  [팀 이름]              [팀 전체 진행률 게이지] │
├───────────────────────────────────────────────┤
│ 멤버별 카드                                     │
│ [이름] [개인 게이지 %] [미완료 N개 (D-1↓ 빨강)] │
│ [이름] [개인 게이지 %] [미완료 N개]             │
├───────────────────────────────────────────────┤
│ 할 일 추가 폼 — 제목 / 담당자 / 마감일           │
├───────────────────────────────────────────────┤
│ Task 목록 (마감 임박/초과는 배경색 강조)         │
│ □ 발표자료 준비 (담당: 이서연, 마감: 9/10)       │
│    └ 로드맵: [x] 자료조사 [x] 초안작성 [ ] 디자인│
│              [ ] 발표연습        (+ 단계 추가)   │
│ □ 회의록 정리 (담당: 김민수, 마감: 9/12)         │
│    (로드맵 없음 — 체크박스로 직접 완료 처리)      │
└───────────────────────────────────────────────┘
```
- 별도 상세 페이지/모달 없이 인라인 편집으로 처리.
- Task마다 로드맵 단계 목록을 펼쳐 보여주고, 단계 추가/완료 체크가 바로 진행률에 반영됨.
- 진입 시 fetch + 60초 폴링으로 갱신.

## 6. API 명세

| Method | Endpoint | 설명 |
|--------|----------|------|
| POST | `/auth/signup` | 회원가입 |
| POST | `/auth/login` | 로그인, JWT 발급 |
| GET | `/teams` | 내가 속한 팀 목록 |
| POST | `/teams` | 팀 생성 (생성자=leader) |
| POST | `/teams/{id}/join` | 초대코드로 팀 합류 |
| GET | `/teams/{id}/dashboard` | 팀 게이지 + 멤버별 진행률 + task(+로드맵 단계) 목록 일괄 조회 |
| POST | `/teams/{id}/tasks` | 할 일 생성 |
| PATCH | `/tasks/{id}` | 담당자·마감일 수정, (로드맵 단계 없을 때만) done 토글 |
| DELETE | `/tasks/{id}` | 할 일 삭제 |
| POST | `/tasks/{id}/steps` | 로드맵 단계 추가 |
| PATCH | `/tasks/{id}/steps/{step_id}` | 로드맵 단계 완료 토글 |

알림(D-1 이메일)은 API로 노출하지 않고 서버 내부 스케줄러가 매일 1회 전체 Task를 훑어 처리 (완전히 끝나지 않은 Task만 대상).

## 7. 기술 스택
- 백엔드: FastAPI, SQLAlchemy, PostgreSQL, APScheduler, smtplib
- 프론트: React (Vite)
- 인증: JWT

## 8. 제외 범위 및 향후 계획
| 항목 | 제외 사유 | 향후 계획 |
|------|-----------|-----------|
| WebSocket 실시간 갱신 | 소규모 팀 규모에서 폴링으로 충분, 복잡도 회피 | 팀 규모 확대 시 재검토 |
| 알림 전용 워커 분리 | 단일 프로세스로 충분 | 트래픽 증가 시 외부 크론으로 분리 |
| Task 상세페이지/댓글/첨부파일 | MVP 범위 밖 | 사용자 피드백에 따라 추가 |
