## 1. 프로젝트 개요

학교 팀플·사이드 프로젝트의 할 일과 마감을 한 화면에 모아, 멤버별 진행률과 마감 임박 항목을 보여주는 대시보드.

핵심 흐름은 다음 4단계다.

1. 팀장이 깃허브 **오가니제이션**을 등록하고 팀이 쓸 레포를 고른다
2. 팀원이 일을 끝내고 **커밋**한다 (커밋 메시지에 `[#3]`처럼 할 일 번호)
3. 팀장이 대시보드에서 **그 커밋을 확인**한다
4. 팀장이 **승인**을 누르면 진행도가 오른다

### 이슈 #1. 회원가입은 되는데 로그인이 안 된다

**증상 (사용자 보고, 09-21 14:00경)**
> "계속 회원가입을 했는데 로그인이 안돼"

**첫 단서 — 서버 로그에 401이 반복**

```
INFO:     127.0.0.1:55330 - "OPTIONS /auth/login HTTP/1.1" 200 OK
INFO:     127.0.0.1:55330 - "POST /auth/login HTTP/1.1" 401 Unauthorized
INFO:     127.0.0.1:55330 - "POST /auth/login HTTP/1.1" 401 Unauthorized
```

**추적 과정** — 추측을 금지하고 4가지 시나리오를 실제 서버에 재현했다.

```
== 재현 1: 정상 가입 → 즉시 로그인
 가입: 200
 로그인: (200, {'access_token': 'eyJhbGciOiJIUzI1NiIs...'})        ← 정상

== 재현 2: 짧은 비밀번호로 가입 시도 (8자 미만)
 가입: 422 {'detail': [{'type': 'string_too_short', 'loc': ['body', 'password'],
        'msg': 'String should have at least 8 characters'}]}
 로그인: (401, {'detail': 'Invalid credentials'})                  ← 재현됨

== 재현 3: 이미 가입된 이메일로 다시 가입
 재가입: (400, {'detail': 'Email already registered'})
 새 비번 로그인: 401
 옛 비번 로그인: 200

== 재현 4: 대문자 섞인 이메일
 가입: 200
 같게 로그인: 200
 소문자로 로그인: (401, {'detail': 'Invalid credentials'})          ← 재현됨
```

**원인 A — 에러 메시지가 `[object Object]`로 표시됨**

422 응답의 `detail`은 **문자열이 아니라 배열**인데, 프론트가 그대로 `Error`에 넣고 있었다.
`api.js`의 코드를 그대로 떼어 실행해 확인했다.

```
$ node -e "const data={detail:[{type:'string_too_short', ...}]};
           const err=new Error(data.detail || '요청 실패 (422)');
           console.log(JSON.stringify(err.message));"
사용자가 보는 문구: "[object Object]"
```

→ 사용자는 **왜 실패했는지 모른 채** 가입을 반복했고, 계정은 만들어지지 않았으므로 로그인은 당연히 401이었다.
"계속 회원가입을 했는데"라는 표현이 이 경로를 정확히 가리킨다.

**원인 B — 이메일 대소문자를 구분**

`Kim@Test.com`으로 가입하고 `kim@test.com`으로 로그인하면 401. 브라우저 자동완성이 대소문자를 바꿔 넣는 경우가 흔하다.

**수정 전에 실패하는 테스트부터 작성** (`tests/test_auth_login.py`)

```
FAILED tests/test_auth_login.py::test_email_is_case_insensitive
FAILED tests/test_auth_login.py::test_same_email_different_case_is_not_a_new_account
FAILED tests/test_auth_login.py::test_short_password_gives_a_readable_message
FAILED tests/test_auth_login.py::test_invalid_email_gives_a_readable_message
FAILED tests/test_auth_login.py::test_missing_field_gives_a_readable_message
5 failed, 1 passed in 0.27s
```

**수정 내용**

- 백엔드: 이메일 저장은 소문자로, 조회는 `func.lower()`로 대소문자 무시 (기존에 저장된 행도 함께 매칭)
- 백엔드: `RequestValidationError` 핸들러를 추가해 422 `detail`을 **한 문장**으로 변환
- 프론트: `detail`이 배열/객체여도 문장으로 푸는 `readDetail()` 방어선 추가 (이중 방어)

**수정 후 실제 응답**

```
A. 짧은 비밀번호  (422, {'detail': '비밀번호는 8자 이상이어야 합니다.'})
B. 이메일 형식     (422, {'detail': '이메일 형식이 올바르지 않습니다.'})
C. Fix2@Test.com 가입 → fix2@test.com 로그인: 200
                       → FIX2@TEST.COM 로그인: 200
D. 중복 가입       (400, {'detail': '이미 가입된 이메일입니다. 로그인해 주세요.'})
E. 비밀번호 틀림    (401, {'detail': '이메일 또는 비밀번호가 올바르지 않습니다.'})
```

**곁가지 — 한국어 조사**

처음 만든 메시지가 `비밀번호은(는) 8자 이상이어야 합니다.`로 나왔다. 받침 유무로 조사를 고르는 함수를 추가했다.

```python
def _josa(word, with_batchim, without):
    last = word[-1]
    has = "가" <= last <= "힣" and (ord(last) - 0xAC00) % 28 != 0
    return word + (with_batchim if has else without)
```

결과: `비밀번호는 8자 이상이어야 합니다.` / `이메일을 입력하세요.` / `이름을 입력하세요.`

### 이슈 #2. 깃허브 연동을 잘못 만들어 전면 교체

**무엇을 만들었나 (1차)**

할 일에 깃허브 **이슈/PR**을 연결하면, PR이 머지되거나 이슈가 닫힐 때 할 일이 **자동 완료**되는 구조. 테스트 7개까지 붙여 실제 레포(`octocat/Hello-World`)로 검증까지 끝냈다.

```
레포 연결: 200 {'repo': 'octocat/Hello-World'}
이슈 연결: 200 [('pr', 1, 'closed', 'Edited README via GitHub')]
  → 할 일 done: True / 자동완료: 2026-09-21T04:23:08
대시보드 진행률: 100 %
```

**그런데 요구사항이 달랐다**

> "1. 팀장이 오가니제이션을 등록한다
>  2. 팀원이 지정된 일을 완료 하면 커밋을 한다
>  3. 팀장이 우리 서비스 화면에서 코드 커밋된걸 확인한다
>  4. 팀장이 완료를 누른다면 진행도가 올라간다."

| 원하던 것 | 만들어진 것 |
|---|---|
| 오가니제이션 등록 | 레포 **하나**만 등록 (`owner/name`) |
| 커밋이 근거 | 이슈/PR만 연결됨, 커밋은 목록 표시만 |
| 팀장이 화면에서 커밋 확인 | 레포 전체 최근 커밋 8개가 뭉쳐서 보일 뿐 |
| **팀장이 눌러야** 진행도 상승 | **정반대.** PR 머지되면 자동으로 상승 |

4번이 정확히 반대였다. "깃허브가 진행률을 자동으로 만든다"와 "커밋은 근거일 뿐, 판단은 팀장"은 완전히 다른 설계다.

**교체 내용** (`c6c4a14`, 21 files, +895 −650)

- `Team.github_repo` 하나 → `github_org` + `team_repos` 테이블(고른 레포만 훑음)
- `TaskLink`(이슈/PR 자동 완료) **삭제** → `TaskCommit`(커밋 증거)로 교체
- 완료 요청(팀원) / 승인·반려(팀장 전용, `require_leader`) 분리
- `task_units()`: 승인만 100%, 단계는 승인 전까지 부분 진행률

**배운 것**: 설계 문서를 쓰고 합의까지 했는데도 어긋났다. 문서에 "이슈/PR이 머지되면 자동 완료"라고 적혀 있었지만, 그것이 **사용자가 그리던 흐름과 같은지**는 확인하지 않았다. 4단계를 문장으로 적어달라고 먼저 요청했다면 1차 구현 전체를 아꼈을 것이다.

### 이슈 #3. `[#N]` 규칙의 오연결 — 깃허브 표기와 충돌

커밋 메시지에서 할 일 번호를 찾을 때 처음에는 `#12` 형태를 그대로 쓰려 했다. 그런데 깃허브에서 `#N`은 **이슈/PR 번호를 가리키는 고유 표기**다.

```
"Merge pull request #6 from acme/patch-1"   ← 6번 할 일에 잘못 붙는다
```

그래서 **대괄호를 요구**하도록 정했다.

```python
# 맨 #12는 깃허브가 이슈/PR을 가리키는 표기라 "Merge pull request #6" 같은 커밋이
# 6번 할 일로 잘못 붙는다
TASK_REF_RE = re.compile(r"\[#(\d+)\]")
```

이 오연결 방지는 테스트로 고정했다 (`test_commit_for_other_task_or_team_is_ignored`).

```python
team["state"]["commits"] = [
    _commit("dead001", "Merge pull request #6 from acme/patch-1"),  # 붙으면 안 됨
    _commit("dead002", "[#99999] 존재하지 않는 할 일"),
    _commit("good001", f"[#{task['id']}] 진짜 이 할 일"),
]
...
assert [x["sha"] for x in commits] == ["good001"]
```

### 이슈 #5. 내가 넣은 버그 — `await` 이후의 `e.currentTarget`

초대코드 복사를 만들면서, 클립보드 실패 시 코드 텍스트를 선택해 주도록 `catch`에 코드를 넣었다.

```javascript
} catch {
  const code = e.currentTarget.querySelector?.('code')   // ← 여기
  if (code) window.getSelection()?.selectAllChildren(code)
}
```

**증상**: 버튼을 눌러도 라벨이 `초대코드 복사` 그대로. 성공도 실패도 표시되지 않음.

```
{"copyLabel":"초대코드 복사"}     ← 'ok'도 'fail'도 아님
```

**원인**: React 이벤트 핸들러가 반환된 뒤 `e.currentTarget`은 `null`이 된다. `await` 뒤에서 접근하니 `TypeError`가 나고, `catch` 블록 안에서 난 예외라 `setCopyState()`까지 도달하지 못했다.

**수정**: `await` 전에 엘리먼트를 붙잡아 둔다.

```javascript
// await 뒤에는 e.currentTarget이 비므로 지금 붙잡아 둔다
const button = e.currentTarget
```

**곁가지 — 더 나쁜 버그를 함께 발견**: 원래 코드는 클립보드 쓰기가 실패해도 무조건 `복사됨`을 표시했다. 사용자에게 거짓말을 하는 셈이라, 실패 시 `복사 안 됨 — 직접 복사하세요`로 바꾸고 코드를 선택해 두도록 했다.

### 이슈 #6. 테스트가 잡아낸 보안 구멍 (구글 OAuth, 이후 철회)

구글 로그인을 붙이면서 "검증되지 않은 이메일이 기존 계정과 겹치면?"을 테스트로 먼저 물었다. 그러자 500이 터졌다.

```
sqlalchemy.exc.IntegrityError: UNIQUE constraint failed: users.email
parameters = [('victim@gmail.com', None, '김구글', None, 'attacker', '2026-09-21 04:54:43')]
```

**의미**: 공격자가 구글 프로필에 남의 이메일(`victim@gmail.com`)을 적어두면, 우리 코드가 그 이메일로 **새 계정을 만들려다** DB 제약에 걸린 것이다. 제약이 없었다면 계정이 뒤섞였을 것이다.

**수정**: 새로 로그인하는 경우 **검증된 이메일만** 허용.

```python
# 검증 안 된 이메일을 받아주면 (1) 남의 이메일로 기존 계정을 노리거나
# (2) 같은 이메일로 계정을 선점해 진짜 주인의 연결을 막을 수 있다
if not identity["email_verified"]:
    raise oauth.OAuthError("구글 계정의 이메일이 확인되지 않았습니다.")
```

테스트 13개까지 통과시켰으나, **이 기능은 최종 산출물에 포함되지 않았다.** 사유는 5장에 기록.

에러가 224/184/212 세 곳에 흩어져 나온 것이 단서였다. 태그 하나가 빠지면 그 뒤의 중첩이 전부 어긋나므로, **가장 위쪽 줄 번호가 아니라 여는 태그를 거슬러 올라가** 확인해야 했다.

### 이슈 #8. 수정했는데 반영이 안 된 줄 알았던 건 — 서버 재시작

조사 선택 로직을 고치고 브라우저를 봤는데 여전히 옛 문구가 떴다.

```
화면: "비밀번호은(는) 8자 이상이어야 합니다."    ← 고친 뒤인데 그대로
```

원인은 코드가 아니라 **`--reload` 없이 띄운 uvicorn 프로세스**였다. 재시작하자 즉시 반영됐다.

```
화면: "비밀번호는 8자 이상이어야 합니다."
```

이후로는 개발 중 항상 `--reload`로 띄웠다.

**같은 부류의 실수 하나 더** — 포트가 이미 점유된 줄 모르고 새 코드를 띄웠다고 착각했다.

```
ERROR:    [Errno 48] error while attempting to bind on address ('127.0.0.1', 8000): address already in use
```

옛 서버(구버전 코드)가 8000을 잡고 있었고, `curl`로 확인한 "정상 응답"은 **옛 코드의 응답**이었다.

## 5. 실패와 삽질 기록

### 5-1. 요구사항을 확인하기 전에 만들었다 (가장 큰 손실)

깃허브 연동을 **두 번** 만들었다. 1차(이슈/PR 자동 완료)는 설계 문서까지 쓰고 테스트 7개를 붙여 실제 레포로 데모까지 마쳤지만, 사용자가 그리던 흐름(커밋 + 팀장 승인)과 방향이 반대라 전량 교체했다. 교체 커밋 하나가 **21개 파일, +895 −650줄**이다.

**무엇을 했어야 했나**: "깃허브 연동을 붙여줘"를 받았을 때, 연동의 *깊이*(OAuth/동기화 방식)는 물었지만 **"그래서 사람이 무엇을 클릭하는가"**는 묻지 않았다. 4단계를 사용자 문장으로 먼저 받아 적었다면 1차 구현 전체가 불필요했다.

### 5-2. 사용자 데이터를 지웠다

데모 환경을 만들면서 `backend/dashboard.db`(기본 DB)를 삭제했다.

```
$ rm -f demo.db dashboard.db
```

이후 확인해보니 그 DB의 사용자는 0명이었다. 사용자가 그 전에 만든 계정이 있었다면 **그때 사라졌다.** "로그인이 안 된다"는 보고에 이 요인도 섞여 있었을 가능성이 있다.

**재발 방지**: 데모용 DB는 `DATABASE_URL=sqlite:///./demo.db`로 분리하고, `.gitignore`에 `backend/demo.db`를 추가했다. 기본 DB는 건드리지 않는다.

### 5-3. OAuth를 두 번 시작해서 두 번 접었다

- **깃허브 OAuth**: `app/oauth.py`까지 작성 → 깃허브에서 OAuth 앱 등록(Client ID/Secret)이 필요해 진행 불가 → 사용자 지시로 중단
- **구글 OAuth**: 전체 구현 + 테스트 13개 통과 → 사용자 판단으로 중단

작성한 코드는 커밋하지 않고 전부 되돌렸다. **외부 서비스 연동은 "계정 등록이 필요한지"를 코드를 쓰기 전에 확인해야 한다.**

다만 이때 내린 설계 판단 하나는 기록해 둘 가치가 있다. 구글 access token을 **저장하지 않기로** 한 것이다. 신원 확인에만 한 번 쓰고 버리면 암호화할 것이 없고, DB가 유출돼도 남의 구글 계정이 넘어가지 않는다. `cryptography` 의존성도 필요 없어진다.

### 5-4. 자잘한 삽질

| 삽질 | 증상 | 교훈 |
|---|---|---|
| 서버 재시작 누락 | 고친 코드가 반영 안 된 줄 앎 | 개발 중엔 `--reload` |
| 포트 점유 | 옛 서버의 응답을 새 코드 응답으로 착각 | `lsof -ti:8000`으로 먼저 확인 |
| 검증 스크립트 오타 | `TypeError: call() got an unexpected keyword argument 'token'` | 일회용 스크립트도 인자 이름을 맞출 것 |
| JSX 블록 치환 | 닫는 태그 유실로 빌드 실패 | 문자열 치환으로 중첩 구조를 건드리면 태그 균형을 눈으로 확인 |
| 조사 처리 | `비밀번호은(는)` | 한국어 메시지는 받침 처리까지 |

### 5-5. 일부러 하지 않은 것

- **할 일 카드 도구줄을 hover로 숨기기**: 화면이 정돈되지만 터치 기기에는 hover가 없어 기능을 못 찾는다. 흐린 글씨로 노출 유지.
- **역방향 동기화**(대시보드 체크 → 깃허브 이슈 닫기): 동기화 루프와 "어느 쪽이 진실인가" 문제를 부른다.
- **웹훅**: 공개 URL이 필요해 사내망·노트북에서 못 쓴다. 폴링으로 시작하되 `sync_repo()` 함수 하나로 두어 나중에 웹훅 엔드포인트가 같은 함수를 부를 수 있게 했다.

이 문서에는 스크린샷 이미지 파일이 포함되어 있지 않다. 개발 중 브라우저 캡처로 확인했으나 파일로 저장해 두지 않았기 때문이다. 제출 시 아래 화면을 직접 캡처해 첨부하면 된다.

5. 팀 화면 `멤버` 탭 — 멤버별 게이지와 깃허브 아이디
6. 팀 화면 `설정` 탭 — 오가니제이션·레포 선택
7. 회원가입 화면에서 `비밀번호는 8자 이상이어야 합니다.` 문구 (이슈 #1 수정 결과)
